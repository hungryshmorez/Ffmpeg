## GL transitions (done, with a speed caveat)
* 48 gl-transitions shaders appear as "GL …" in the transition list (also in random picks, favourites, saved projects) when the installed FFmpeg's `xfade` supports custom expressions (`Capabilities.xfade_custom`; true for the Linux 6.1 test build and the pinned Windows 7.1.1 build in CI).
* Verified: `tests/glx.rs` runs every one through real FFmpeg (starts on A, ends on B, differs from both during the transition; a hang fails after 60 s) and three go through project → export → save/load.
* **Slow:** they are evaluated per pixel by FFmpeg's expression engine. Measured on this 4-core sandbox at 1080p: about 2.3 s/frame (gl_angular) to 5.5 s/frame (gl_crosswarp); at 960x540 about 0.6–1.4 s/frame; gl_linearblur is ~4× slower still. A 1 s transition at 25 fps therefore costs roughly 1–2.5 minutes of export at 1080p. Use the preview scale while editing. The transition lists mark them "(slow to render)"; native transitions stay instant.
* **12 more wipes** written by hand for FFWORKS (`assets/glx/ffworks_wipes.tsv`, listed as "GL Wipe …": radial in/out, diamond, clock, barn doors, square iris, blinds, slices, dissolve, pixel blocks, spiral) go through the same per-pixel path and the same all-transitions test; they are FFWORKS originals, not gl-transitions code.
* Not available: ~75 other gl-transitions shaders (textures, loops, multi-pass), 14 of which xfade-easing only supports in its patched FFmpeg. Not faked.

## Audio-reactive parameters ("Follow audio", done)
* The ♪ button next to any animatable parameter (clip opacity/transform, effect parameters such as brightness, an audio clip's volume) makes it follow the loudness of the clip's linked audio (or the audio clip itself): set the value for quiet and for loud, a smoothing time, and optionally one frequency band (bass < 150 Hz, mids 300 Hz–3 kHz, treble > 5 kHz; done with FFmpeg low/high-pass filters before measuring). Command `AnimateFromAudio` measures RMS level 20×/s with FFmpeg (`astats`), normalises between the quiet floor (10th percentile) and the loudest moment, smooths, and writes ordinary keyframes (thinned with Ramer–Douglas–Peucker to ≤200 keys within 1% of the curve) through the new general `SetKeyframes` command — so it previews, renders, saves, undoes (one step) and can be edited afterwards. Macros and the CLI can use both commands.
* Tested: `tests/reactive.rs` (quiet/loud step source → exported brightness differs by >60 luma levels between the halves; save/load keeps the curve; undo removes it; out-of-range values and following a video clip are refused before FFmpeg runs; an audio clip's own volume; bass/treble bands each follow only their half of a 60 Hz → 6 kHz source), unit tests for parsing/normalising/smoothing/thinning, GUI test `scripts/uitest/reactive.sh` (12/12 with beats mode).
* **Beats mode** (`AnimateFromBeats`): the parameter jumps to the "on the beat" value at every onset found by FFWORKS's beat detector and eases back to the "between beats" value over a decay time, holding until the next beat (≤150 beats per curve; split longer clips). Tested: clicks at x.4 s → exported frames on the beats are >100 luma levels brighter than between them; undo; GUI (same script, 12/12 total).
* Limits: no spectrum analysis beyond the three bands; the source must be at 100% speed, not reversed/frozen; MIDI files, expressions and LFO modulators were added later. The Tauri `dispatch` command is now async so measuring never blocks the window.

## LFO modulators (done; the "baked" half of modulators)
Every animatable field has a ∿ button next to ◆ and ♪: pick a shape (sine, triangle, saw, square, random), rate in Hz, low/high and where in the cycle to start; Apply writes ordinary keyframes (`AnimateFromLfo`, `reactive::lfo_keys`), so previews, export, save/load, undo and hand editing work exactly as for any keyframes. Sine uses eased segments between its peaks (two keys per cycle, within ~2% of a true sine at frame-aligned rates); square holds; saw rises and drops; random glides between seeded random values (same on every machine).
* **Limits:** keyframes, not live expressions: the 200-key cap (each key nests an `if()` in the FFmpeg expression) means rate × clip length is bounded (about 100 cycles of a sine; the error says so and suggests a lower rate or a split clip); at most fps/4 Hz; half cycles snap to frames, so the shape at rates that don't land on whole frames is off by up to a frame; starting mid-wave (phase ≠ 0) approximates the first partial segment. **Not done:** live modulators that compile to FFmpeg expressions (`sin(2*PI*f*t)`) with no key limit, links that stay live when the source changes. MIDI files are done (see MIDI).
* **Tests:** 4 unit tests (shape accuracy, phase/range, square/saw/random, refusals), `tests/lfo.rs` 3 real-FFmpeg tests (square blinks in the export at the right seconds, sine glides and is one undo step, refusals leave no keys), 5 steps in `reactive.sh` (now 16).

## Adjustment layers (done)
Timeline toolbar → "+ Adjustment" puts a layer at the playhead (5 s, topmost free video track, or a new top track). Effects added to it (any video effect, including custom graphs and frei0r) apply to **everything composited beneath it** for as long as the layer lasts; its opacity sets how strongly (keyframable, like any clip). A `crop` effect on the layer limits where it applies (the cropped-away part stays unadjusted). It is a normal clip with `adjustment: true` (absent from the JSON otherwise) on the transparent canvas; the renderer splits the picture composited so far, cuts the copy to the layer's span (half a frame early, like source trims), runs the effects and lays it back over (`ffmpeg.rs`, `VideoSegment.adjustment`).
* **Refused with a reason:** blend mode, position/scale/rotation (incl. keyframes), speed, reverse, freeze, transitions, pixel sort (needs footage of its own), placing on an audio track or over another clip. Random looks skip pixel sort for layers.
* **UI:** striped clip on the timeline; the monitor's source view keeps showing the footage beneath (the layer paints nothing) and shows the "bypassed" badge while a layer with effects is under the playhead; a rendered preview shows the result.
* **Tests:** 8 real-FFmpeg tests in `tests/adjustment.rs` (exact first/last adjusted frames, half-strength opacity, effects see *all* lower tracks, crop limits the area, preview starting inside the layer, refusals, save/load/undo, random looks), GUI `adjustment.sh` 10 checks, a monitor unit test.
* **Not done:** a layer can't be limited to some tracks only; effects that need footage metadata (frei0r sources/mixers are not offered anyway) are untested on layers; no layer-specific timeline resize handles beyond the usual trim.

## Pixel sort (built in, done)
Effects panel → Glitch → "Pixel sort". FFmpeg has no filter that can reorder pixels by value, so FFWORKS does it itself (`pixelsort.rs`, `bake.rs`); it works the same on Linux and Windows and needs no plugin.
* **What it does:** sorts runs of pixels along rows, columns or any angle (the Angle setting turns the direction by -90..90°; spans then follow lines of pixels one pixel apart, planned once per bake) by brightness, hue, saturation, value, red, green or blue, low→high or reversed. Which pixels form a run: those inside a brightness range (Asendorf-style), whole lines, or random-length blocks (length, variation, seed, optional new blocks every frame). "Amount" blends sorted and original. All settings are ordinary effect parameters (undo, save/load, macros, random looks, saved looks).
* **How it runs:** the effect keeps its place in the stack. Before the render, `bake::prepare` plans one *stage* per clip use (or transition side) that carries a sort: FFmpeg renders that use up to the sort (speed, reverse, title, earlier effects included) as raw RGB on a pipe, Rust sorts each frame (counting sort, rows spread over threads), FFmpeg stores it losslessly (FFV1). The render graph then reads that file and applies only the later effects, so colour, keyframes, transitions and blends after the sort work unchanged. `jobs::run_job` runs the stages first (they take the first share of the progress bar); the stage list lives in `FfmpegJob` so queued exports survive the unfinished-exports journal. Exports delete their bake files when they end; previews bake only the range they show (plus a frame of margin), keep the file in `<cache>/bake` and reuse it when only something *after* the sort changes (cache trimmed to 4 GB, never touching files used in the last 10 min). Cancel kills both FFmpeg processes and leaves no partial file. The Command Inspector shows the main render; the sort stage is not in that text.
* **Tests:** 9 unit tests (sort order, thresholds, reverse, vertical, amount, keys, seeds, parameter clamping), 11 real-FFmpeg tests in `tests/pixelsort.rs` (rows/columns really sorted in the exported picture, only in-range pixels move, stack order, retimed clip, transition side, partial preview + reuse of the bake, unbaked graph refused, save/load/undo, cancel), GUI `pixelsort.sh` (12 checks: add from the panel, real preview and queued export measured as sorted, two undo steps). Registry-wide tests (`every_registered_effect_renders_in_real_ffmpeg`, random stacks) now plan the sort the way `compile_project` does.
* **Limits:** a sorted picture is opaque (transparency is composited on black first); the sort always runs at project resolution, even for low-quality previews; a sort is reused across exports and previews while its source, range and settings are unchanged (see "Smart reuse" below); sorting is CPU-only (about tens of frames per second at 1080p in a release build — unmeasured here). The preview button shows a percentage while a sort bakes.

## Pixel sort: keyframed settings and masks (done, Linux-verified)
* **Keyframes:** the amount, brightness range (from/up to), block length and variation, angle and the mask's position, size and soft edge can be animated with the usual ◆ buttons. The bake reads each frame's settings from the clip's keyframes (clip-relative time, so a sort can fade in, sweep, change angle over time). The angle snaps to whole degrees so the line plan is reused until it really changes (an animated angle is slower: each new angle re-plans the picture). Animated bakes are keyed by their keyframes, so editing a key makes a new cached bake and a static sort still reuses its own.
* **Masks:** "Only inside a shape": none, rectangle or ellipse, with centre, size, soft edge (px) and an invert switch (sort outside instead). The sort really stops at the shape: pixels outside never move and runs are cut at the edge (rather than sorting everything and cropping, which would drag outside pixels in). The soft edge fades the sorted picture back into the original.
* **Tests:** 5 new unit tests (outside untouched and runs stop at the edge, invert, ellipse corners and the soft edge, keyframes read per moment, mask settings clamped) and 3 real-export tests in `tests/pixelsort.rs`: a keyframed amount goes from the original to fully sorted (measured against the source frame), a left-half mask leaves the right half within 2% and puts the left half in order, an animated ellipse travels left to right and is cached separately from a static one.
* **Not done:** luma/picture masks (a shape drawn from another clip), masks that follow motion, keyframed mode/direction/key/seed (discrete settings), GPU sorting.

## Mosh lab: real motion-vector datamosh (done, Linux-verified)
Effects panel → "Datamosh lab…" (video clips). FFglitch (a separate GPL tool; found via saved folder > installer's `ffglitch/` > `FFWORKS_FFGLITCH` > `PATH`; the dialog says so and takes a folder when it is missing) rewrites the *motion vectors* inside the compressed stream, which stock FFmpeg cannot. It is a lab, not a live effect: it makes a **new file** and puts it on a new "Datamosh" track at the original's place and length (the original clip is untouched; import, track and placement are three undo steps).
* **Pipeline (`moshlab.rs`):** ffmpeg decodes the clip's source range at project size/rate → pipe → `ffgac` writes an all-P MPEG-4 AVI with a wide vector range (`-fcode 6`, which stock FFmpeg lacks) → `ffedit` runs a script → ffmpeg stores the result as FFV1 MKV in `<app data>/mosh`. Modes: amplify (×0–16), drift (push every vector by x/y half-pixels), borrow (export another clip's vectors with `-e`, apply with `-a`; the shorter length wins). Scripts clamp to the stream's range; an out-of-range warning from ffedit is turned into an error. Progress is per stage (35% / 70% / 100%), not per frame. Cancel kills every child; nothing is left behind.
* **Limits:** works on the footage at normal speed (speed/reverse/freeze/titles/stills are refused with the reason); effects, transform and opacity of the original clip are not copied; the intermediate is lossy MPEG-4 (that is part of the look); results are lossless FFV1 so large.
* **Found by measuring:** FFglitch hands `-sp` parameters to `setup()` as `args.params`; the first version read `args.factor`, silently used its defaults, and the tests still passed until they compared amplify ×1 against ×4 and drift +6 against −6. The old trial script had the same latent flaw (hidden because its default matched).
* **Tests:** 6 real-FFglitch tests in `tests/moshlab.rs` (they skip with a printed note without FFglitch, and *fail* when `FFWORKS_REQUIRE_FFGLITCH` is set, which CI does), 4 unit tests, GUI `mosh.sh`. CI downloads the pinned Linux 0.10.2 build; the Windows job bundles the pinned Win64 zip (ffedit/ffgac, ~60 MB uncompressed) and runs the same tests with the bundled tools after uploading the installer.
* **Unverified:** everything on Windows (argument quoting of the `-sp` JSON through `ffedit.exe`, pipes into `ffgac.exe`) until CI reports; the look on real footage was judged by pixel differences, not by eye; H.264 sources are fine (they are re-encoded), H.264 *output* is not possible (FFglitch cannot edit it).

## Corruption lab (done, Linux-verified; needs only FFmpeg)
Effects panel → "Corruption lab…" (video clips). Real bitstream damage: the clip's source range is encoded with an old codec (MPEG-4, MJPEG or MPEG-2, keyframes every N frames), FFmpeg's `noise` bitstream filter damages the *compressed packets* (bit damage level 1–10 = one damaged byte per 204 800 … 400 bytes; and/or every N-th packet dropped, never the first), and the wreck is decoded (`-err_detect ignore_err`), retimed to the project rate and stored as FFV1. Errors therefore behave like real corruption: they smear until the next full picture, tear blocks or colours, or freeze where packets are missing. Like the mosh lab it is a lab, not a live effect: it makes a **new file** placed on a new "Corruption" track at the clip's place and length (import, track, placement = three undo steps); the original is untouched. It runs as a queue task (`lab:corruption`, cancel from the dialog or the Queue panel; FFmpeg is killed, nothing is left behind).
* **Verified:** `tests/corruptlab.rs` (8) with real FFmpeg on 6.1 and a current build: damage grows with the level (PSNR against the original: level 9 at least 6 dB lower than level 2), 75 frames in = 75 out, the damaged bytes are identical for identical settings (and differ for other settings), dropped packets freeze the picture without shortening the clip, all three codecs work and look different, keyframe spacing changes the result, a raised cancel token stops at once with no partial files, bad requests and missing sources are clear errors, the result lands on its own track and the original keeps its clip; 2 unit tests. GUI `corrupt.sh` (17 steps): the button, dialog controls, Make disabled with nothing to break, the new track/clip/media, three undos, the queue job, a refusal, a 30 s clip cancelled within seconds with nothing added and no leftover temp folders. `a11y.sh` scans the dialog.
* **Honest limits:** *which bytes break* is repeatable, but FFmpeg's decoders conceal broken data in ways that are not exactly repeatable from one run to the next (measured on both builds: some frames differ between runs), so the finished picture can differ in small details; that is why the result is kept as a file. H.264 and HEVC are not offered (their decoders are far less forgiving and libx264 is not in every build). No seed control, no per-region damage, no audio corruption, and the look was judged by measurements, not by eye.

## Cancelling previews, and previews/analyses in the job queue (done, Linux-verified)
A processed preview used a cancel token nobody could trigger, so a long pixel sort or compound render could not be stopped. Now previews **and analyses** are *tasks* in the same job queue as exports (`JobQueue::run_task`): they are listed in the Queue panel with progress and a Cancel button, report failures with the reason, and are cancelled from the Monitor's **Cancel** button or the Queue panel (same job). A new preview cancels an older one; "Preview canceled" is an info toast, not a failure.
* **What runs as a task:** the preview render, beats, scenes, silence/black/freeze ranges, loudness, auto-sync and the scopes (operations `preview` and `analysis:*`). **Not** tasks: waveforms and thumbnails (many tiny calls) and the one-off `list_*`/probe calls.
* **Cancelling really stops FFmpeg:** `process::run_cancellable` polls the token and kills the child; `beats/loudness/detect/audiosync/scopes/scenes` have `*_with(…, &CancelToken)` variants and the old functions are wrappers with a token nobody raises. A cancelled analysis writes no cache file; the preview leaves no partial files.
* **Does not wait behind exports:** tasks run on their own threads beside the render workers (a long export must not hold up a preview), so they do not count against the worker limit. They are never written to the crash journal and have no FFmpeg log (the Queue panel hides the Log button for them).
* **Tests:** `tests/tasks.rs` (7: listed while running with progress and Completed visible before the result arrives, cancel from the queue, failure and panic reported instead of hanging, never journalled, shutdown cancels tasks, a real endless FFmpeg is killed within seconds, every analysis returns `Canceled` for a raised token and leaves no cache, same results as the plain functions) and `queue_tests::a_task_does_not_wait_behind_a_running_export`. GUI test `scripts/uitest/previewcancel.sh` (15 steps): the preview is a queue job with a description, cancelled from the Monitor and again from the Queue panel, an analysis appears in the queue and a failing one carries the reason, then a normal preview and no partial files.
* **Not done:** progress inside analyses (they show an indeterminate bar), resuming a cancelled analysis, a task limit (a user can start many at once).

## Smart reuse of rendered intermediates (done, Linux-verified)
Pixel-sort bakes and compound-clip renders are files in a content-keyed cache (`<cache>/bake`, trimmed to 4 GiB, least recently used first, never anything used in the last 10 minutes). Previews and compounds always used it; **exports now do too** (they used to delete their bakes and re-sort every time). Exporting again after an edit that does not touch a sorted clip (another clip, an effect added after the sort, a title, audio) reuses the sorted frames; changing the sort's settings, its source range or the project size/rate makes a new file. `tests/pixelsort.rs::a_second_export_after_an_edit_elsewhere_reuses_the_sorted_frames` proves it by satisfying the second export's stage with an FFmpeg that cannot run.
* **Costs:** the lossless FFV1 files stay on disk after an export (up to the 4 GiB limit, shared with previews).
* **Not done (honest):** segment-level smart rendering of the *main encode* (re-encoding only the changed span of a finished export) and resuming a half-finished export after a crash: the final encode still restarts from the beginning. Segmenting needs closed GOPs, matching audio priming and a stream-copy join, and was judged too risky to ship without a Windows machine to verify it on.

## Media library (SQLite index, done, Linux-verified)
`<app data>/library.sqlite` remembers every source file imported into any project on this machine (path, name, content fingerprint, size, length, picture/sound, picture size, first/last seen); `library.rs` over bundled SQLite (`rusqlite`), layout versioned with `PRAGMA user_version` (a database from a newer FFWORKS is refused, not damaged). It is filled wherever media joins the open project (import, open, recover, relink) in one transaction, never reads media itself, and ignores generated media. Palette → "Media library: find files imported before…": search by any words of a name or folder (case-insensitive, `%`/`_` are literal), see which files still exist, import one with a click, "Forget missing files". **Relinking** asks the library first: if another project saw the same content (fingerprint, or the same name and size) somewhere that still exists, that folder is searched too, so a moved or renamed file is found without anyone choosing the folder.

## MIDI files as a parameter source (done for files; live devices are not)
A Standard MIDI File (`midi.rs`, parsed with `midly`) drives any animatable parameter: the ♬ button next to a slider (beside ♪ audio, ∿ LFO, ƒ formula) picks a `.mid` file and what to follow: a **controller** (`cc:0`–`cc:127`: mod wheel, volume, expression…), **note velocity** (a pulse per note as high as its velocity, falling back over a decay time), **gate** (high while any note is held), **pitch** (the latest note's key) or the **pitch wheel**; optionally one channel (1-16), a minimum/maximum, and how many seconds after the project start the file begins. Timing comes from the file's own tempo map (tempo changes on any track, ticks or SMPTE timecode). Result: ordinary keyframes in one undo step ("Follow MIDI with <param>"), so everything that already works with keyframes (editing keys, split, copy, rendering) applies. A clip placed late in a song starts at the value the controller was holding; dense controller sweeps are thinned to 200 keys within 1%; more notes than fit are refused with a message to split the clip.
* **Command:** `animate_from_midi { clip, param, path, source, channel?, track?, low, high, decay?, offset? }`. It reads a file, so scripts, plugins and the local API refuse it (like `import_media`).
* **Tests:** `tests/midi.rs` (12): tempo map across tracks, velocity-0 note-offs, controller mapping, gate, velocity pulses and pitch, pitch wheel, channel/track filters, a clip starting mid-song and the offset, bad inputs, thinning and the too-many-notes refusal, the command with undo and validation, scripts refused. GUI test `reactive.sh` (28 steps, 6 new): the panel's controls, Apply disabled without a file, a real `.mid` file written by the test becomes the expected keyframes, undo.
* **Not done:** **live MIDI devices** (a keyboard or controller feeding the project in real time; needs `midir` and hardware this environment lacks), MIDI *output*, per-note parameter targets, importing a MIDI file as notes/markers on the timeline, and the native file dialog is not exercised by the GUI test (the command is called with the path).

## Colour management (done for Rec.709 projects, Linux-verified)
The project is Rec.709 SDR. Footage whose file says otherwise is converted on the way in (`colormgmt.rs`, decided from the probe's colour tags, shown in the Command Inspector as part of the filter graph): **BT.601** (`smpte170m` / `bt470bg`) and **BT.2020 SDR** get `colorspace=all=bt709:iall=…` (matrix and primaries); **PQ and HLG HDR** are tone-mapped to SDR through linear light (`zscale` → `tonemap=hable` → `zscale` back to Rec.709; needs `zscale` and `tonemap` in the FFmpeg build, which gyan "essentials" and "full" have, and the render says so if they are missing). Untagged or Rec.709 footage is untouched: a project without such clips compiles exactly as before. **Every video export is now tagged Rec.709** (`-colorspace/-color_primaries/-color_trc bt709`; not for PNG/GIF/raw), so players stop guessing the matrix from the resolution.
* **Applies to** ordinary footage in clips and in transition sides; baked pixel sorts and compounds are rendered from the converted picture. **Not applied to** stills/generated media (treated as sRGB/709).
* **Tests:** 4 unit tests (tag → conversion table), 5 real-FFmpeg tests in `tests/colour.rs`: BT.601 lime comes out within 12 of the intended colour while the identical pixels labelled Rec.709 are >25 off (a control), BT.2020 changes the picture and stays blue, HDR PQ grey is tone-mapped to a neutral plausible SDR level and the export is tagged, every export carries Rec.709 tags, untagged footage is left alone.
* **Not done:** a project colour-space setting (Rec.2020/HDR output, P3), per-clip override of a wrongly tagged file, LUT/ICC handling, tone-mapping controls (hable is fixed), HDR *output*, scopes in the source colour space. The tone-map level was checked only as "neutral and plausible", not against a reference grade; UNVERIFIED on real phone HDR footage.

## Local API (done, Linux-verified)
Diagnostics → "Local API" (off by default) or `ffworks serve <project|new> [--port N] [--token T] [--allow-analysis]`. The same command bus the editor uses, over HTTP, so another program on this machine (a stream deck, a build script, a notebook) can edit the open project: `GET /v1/status`, `GET /v1/project`, `POST /v1/command` (one command, the same JSON as command lists and macros), `POST /v1/commands` (a list: one undo step, all or nothing), `POST /v1/script` (`{"source": "<Rhai>", "selected": "<clip id>"}`), `POST /v1/undo|redo|save`. Errors are `{"error": "..."}` with 400/401/403/404/405/413. Edits made through it appear in the open editor at once (a `project-changed` event refetches the state) and are ordinary undo steps.
* **Safety (`api.rs`):** listens on `127.0.0.1` only; every request needs `Authorization: Bearer <token>` (128-bit random, compared in constant time, kept in settings until you press "New token"); a request carrying an `Origin` header (any web page) is refused, as is a `Host` that is not the server's own loopback address (DNS rebinding); bodies are limited to 1 MiB; `import_media` / `relink_media` (they read files) are refused, and audio analysis commands are refused unless the server is started with analysis allowed (the app does not allow it); scripts run in the Rhai sandbox.
* **Tests:** 10 real-HTTP tests in `tests/api.rs` (loopback only, token, Origin/Host refusal, command + change notification, undo/redo and error messages, atomic command lists, script sandbox and analysis permission, path/method/size refusals, stopping closes the port, short tokens refused), 2 unit tests, `ffworks serve` by hand with curl, GUI `localapi.sh` (starts from saved settings, curl edits the project from outside and the editor shows it, the editor's own web page is refused, the switch and the closed port).
* **Not done:** HTTPS/remote access (deliberately not offered), an event stream for external clients, per-endpoint permissions, an API for rendering/exporting (use the CLI), and per-plugin API permissions (plugins are in, see Plugins).

## Expressions and parameter links (done, Linux-verified)
Any animatable parameter has a **ƒ** button next to the LFO (∿) and audio (♪) ones: type a formula, optionally say what `v` is (another parameter of the same clip), optionally clamp, Apply. Like the LFO it is **baked to ordinary keyframes** (a one-off calculation, not a live binding: change the source or the clip's length and apply again), so it previews, renders, saves, undoes and edits like hand-set keys. Command `AnimateFromExpression`, one undo step ("Formula on <param>"); scripts get `animate_expr(clip, param, formula)` and `link_param(clip, param, source, formula)` (clamped).
* **Formula language:** [fasteval](https://crates.io/crates/fasteval) (MIT): `+ - * / % ^`, comparisons, `if`, `sin cos tan abs min max floor ceil round sqrt log exp int sign pi() e()`, plus the variables `t` (seconds into the clip), `p` (progress 0–1), `n` (frame), `d` (clip length), `fps`, `v` (the source parameter's value at that moment; default: the parameter's own current value) and `noise(x)` (smooth deterministic noise 0–1). Evaluated once per frame (every few frames on clips over 200 frames), then thinned to the fewest keys that stay within 0.2% of the range (at most 200); a straight ramp becomes two keys.
* **Refusals (nothing changes):** syntax errors and unknown names (with fasteval's message), a result that is not a number at some time (division by zero) and says when, a result outside the parameter's range (says the value, the time and the range) unless clamp is on, a parameter FFmpeg cannot animate, an unknown or unreadable source. Sources can be clip parameters or `fx:<effect id>:<param>`; the UI offers the clip-level ones.
* **Tests:** 8 unit tests (`expr.rs`), 5 real-FFmpeg tests in `tests/expr.rs` (a ramp measured in the export, a link measured in the export, undo/save/load, an effect parameter, refusals), a script test, and GUI steps added to `reactive.sh`.
* **Not done (still open from Phase 6):** live modulators compiled into the FFmpeg expression (so no baking), links that stay live when the source changes, live MIDI devices (`midir`; MIDI files are done) and a custom effect builder.

## Compound clips (done, Linux-verified)
Palette → "Make a compound clip from the selected clips" (Shift+click selects several; linked audio comes along). The clips fold into ONE clip on the timeline whose contents are a sequence of their own: double-click it (or palette → "Open the selected compound clip…") to edit what is inside with the ordinary tools, "← Back to the main timeline" to return. "Take the selected compound clip apart" puts the contents back on new tracks (trimmed to what the clip showed); "Fit … length" shortens its source to match its contents.
* **Model:** a compound is ordinary media (`Generator::Nested { sequence }`) pointing at a `Sequence { compound: true }`, so trim, speed, effects, transform, blend, opacity, transitions, linked audio and keyframes all work on it unchanged. Commands `NestClips`, `UnnestClip`, `FitCompound` (all one undo step, planned as patches in `nest.rs`); which sequence is shown is not an undo step (`Engine::set_active_sequence`; undo that removes the shown sequence steps back to the main timeline). The compound's media length grows by itself as its contents grow (same undo step) but never shrinks. A compound cannot contain itself (validation) and may nest 8 deep.
* **Rendering:** `nest::prepare` renders each compound's sequence once, through the normal compiler, to a lossless FFV1 + FLAC cache file named after a hash of its render and source files; the outer render reads that file like any source. Inner compounds and pixel sorts are rendered first (`FfmpegJob.nests`, run by `jobs::run_job` before the sorts, progress shared). Unchanged compounds are reused (preview and export share the cache, trimmed with the bake cache); a change inside gives a new key. Two renders of the same compound never share a partial file.
* **Limits:** the inside is opaque (composited on black like any export) and is rendered at project resolution and frame rate whatever the preview quality; the whole compound is rendered even when only a few seconds show; no live preview of the inside in the monitor except through a rendered preview (the monitor shows the generic "generated clip" note); taking apart refuses a compound that has its own speed/effects/transform/blend/opacity/volume/fades/keyframes or a transition; nesting refuses a selection that would swallow an unselected neighbour or tear a transition; the new Compound sequences are hidden from snapshots but appear in the project file.
* **Tests:** 15 real-FFmpeg tests in `tests/compound.rs` (pixels and loudness measured: same picture before/after, undo/redo exactness, effects/trim on the compound, edits inside show outside, growth and fit, reuse from the cache without FFmpeg, two levels, cycle refusal, take apart incl. trimmed, refusals, save/load, sound stays linked and at level), GUI `compound.sh` 10/10 (palette → double-click → edit inside → back → take apart → two undos).

## Plugins (Extism / WebAssembly) — done, Linux-verified
A plugin is a folder with `plugin.json` and a `.wasm` file (any language with an [Extism](https://extism.org) plugin kit). It receives the project as JSON and answers with a list of ordinary commands; the host applies them as ONE undo step, all or nothing, through the same checks scripts have. Full interface, limits and an authoring walk-through: `docs/PLUGINS.md`. Palette → "Install a plugin from a folder…" copies it into `<app data>/plugins/<name>/`; every installed action then appears in the palette as "Plugin <name>: <action>". CLI: `ffworks plugin <folder>` lists the actions, `ffworks plugin <folder> <action> <project|new> [--dry-run] [--save out] [--selected id]` runs one.
* **Sandbox:** by default no network, no file system, no host functions; at most 10 s per call, 64 MiB of memory, 4 MiB of answer, 2000 commands. **Every Extism feature is enabled** (HTTP, WASI, config, file/URL module sources, wasmtime exceptions) but each one is a request in the manifest that stays **off until the user grants it**: hosts (Plugins dialog / `--allow-host`), folders (`--allow-folder /guest=/real`, read *and* write), `wasi: true`, `config`. See `docs/PLUGINS.md`. `import_media` / `relink_media` are refused; media analysis needs the manifest to ask for it *and* the caller to allow it (the UI never does). A plugin that is not allowed to edit is refused outright.
* **Tests:** `tests/plugin.rs` (10, against the committed example plugin `plugins/example`, built from `src/lib.rs` by `build.sh`): reads the project and adds markers as one undo step (undo/redo restore the exact project), the selected clip reaches it, file reads / unrequested analysis / read-only grants are refused, a failing second command undoes the first, garbage output and a missing export are clear errors, a runaway loop ends with "timeout", a 256 MiB allocation with "oom", a manifest cannot point outside its folder, installing copies only the manifest and the wasm and replaces an older copy. GUI test `scripts/uitest/plugin.sh` (14 steps) installs it through the real app, finds its actions in the real palette, runs one, undoes it, and checks the refusals.
* **Tests:** also `a_plugin_reaches_the_network_only_for_hosts_it_asked_for_and_was_given` (a local web server counts requests: 0 reach it without the grant or for an unrequested host), `a_plugin_reads_its_fixed_config`, `a_wasi_plugin_sees_only_the_folder_it_was_given` (reads and writes its folder, cannot read /etc/passwd, a folder granted under an unrequested guest path or a missing folder is refused); GUI `plugin.sh` now 21 steps incl. the Plugins dialog allowing a host and a real HTTP call to a local server.
* **Not done:** a plugin store/registry, signing or hashes for plugins, host functions of FFWORKS's own (so a plugin cannot ask the host for a frame or an analysis result), plugins that add effects/filters/export presets, per-action permission prompts, hot reload, a plugin UI panel, read-only folder grants (Extism maps the folder read-write), per-call (instead of saved) grants in the UI. UNVERIFIED on Windows (the same wasmtime engine, but only Linux has run the plugin tests locally; CI builds and runs them on Windows).

## Scripting (Rhai) — done, Linux-verified
Palette → "Run a script (Rhai) on the project…" and CLI `ffworks script <project|new> <file.rhai> [--dry-run] [--save out] [--selected <clip>] [--allow-analysis]`. [Rhai](https://rhai.rs) (MIT/Apache-2.0) gives real variables, loops, conditions, functions and maps on top of the existing JSON command lists (`ffworks run`, macros stay as they are).
* **Same command bus:** every function a script calls issues an ordinary `Command`; the whole run is **one undo step** (`Engine::begin_group/end_group`), and any error (syntax, runtime, refused command, limit) rolls every change back (`abort_group`) so nothing half-applies. Save/load/render are therefore unchanged.
* **Reads:** `project()`, `tracks()`, `clips()`, `media()`, `selected()`, `print(...)`. **Writes:** `add_effect`, `set_param`, `remove_effect`, `set_opacity`, `set_gain`, `set_speed`, `add_marker`, `split`, `delete`, `move_clip`, `add_track`, `place`, `add_title`, `add_solid`, `add_adjustment` (the creators return the new id), `animate_lfo`, and `command(#{ type: "...", ... })` for every other command (same JSON as the command lists; a wrong shape says which part is wrong).
* **Permissions and limits:** a script has no file, network, process or module access (Rhai built without modules; `import_media`/`relink_media` are refused because they read files). Two permissions: *edit* (off = dry run, every edit is refused) and *analysis* (needed for `animate_from_audio` / `animate_from_beats`, which run FFmpeg over the project's audio; the CLI flag `--allow-analysis` grants it, the app does not grant it). Limits: 3 million operations, 32 call levels, 20 s run time, 2000 commands, 200 KB source; an endless loop is stopped, not hung.
* **Tests:** 9 integration tests in `tests/script.rs` (loops/conditions/undo as one step, read functions, creators and ids, adjustment + LFO helper, the generic `command`, errors with line numbers, rollback on failure, no way to reach files/modules/programs, dry run, limits), the CLI by hand (new project → save → dry run), GUI `scripts/uitest/script.sh`.
* **Not done:** a script editor panel (scripts are files you pick), macro variables inside recorded JSON macros, scripting of analysis results beyond the two follow commands, (plugins and the local API are in).

* Proxies: the file properties are verified (960x540 H.264/AAC), but whether a proxy plays in a webview that cannot decode the original (e.g. ProRes on Windows WebView2) is unverified: this sandbox webview cannot decode H.264 at all, so only the "original fails → offer proxy → proxy created" path was exercised. Markers aren't exported as chapters yet.
* Research notes: OpenShot (libopenshot LGPL-3) and Audacity (GPLv3) are reference only; do not copy their code into FFWORKS. Candidate FFmpeg-filter effects inspired by them: chroma key, mask, deinterlace, pixelate, phaser/chorus/flanger, gate, de-click.
* Titles: no per-letter animation/typewriter, no rich text (one style per title), no title preview in the source monitor (rendered preview only). Fonts are found by file name; fonts on another computer must exist there. Subtitle files (SRT) and image *sequences* are not imported yet; GIFs play once (no loop option).
* Mixer meters are *predicted* from analysed waveform peaks (gain/fades/pan applied, effects not) — not live audio levels; no master meter. Source playback in the monitor can't preview pan/fades/effects (rendered preview/export only). No reverb/pitch-shift/de-esser. Pan can't be keyframed.

* Native open/save dialogs and the close-confirmation prompt aren't exercised by GUI tests (tests call the same backend commands).
* Preview invalidation is whole-project, not per time range. Undo history isn't restored after crash recovery.

## Decisions (don't relitigate without reason)
* Bundle GPL FFmpeg 7.1.1 in the Windows installer (H.264 export needs libx264). FFWORKS runs it as a separate process. Notices in `THIRD_PARTY_NOTICES.md`; user can override via Diagnostics.
* Tool lookup order: saved setting > `FFWORKS_FFMPEG`/`FFWORKS_FFPROBE` > bundled > PATH.
* Transitions are centred on the cut and use media handles (timeline length unchanged).
* Project JSON uses rational strings `"n/d"` for times; schema version 1 with `serde(default)` for new fields.
* Source preview is honest: effects only appear in a *rendered* preview, with a visible "bypassed" badge otherwise.

## FFglitch trial (Phases 8–9 design input)
Tried FFglitch 0.10.2 (Linux x86_64 static build from ffglitch.org, GPL-2+) on real generated clips. Reproduce with `FFGLITCH_DIR=<unpacked dir> ffworks/scripts/ffglitch/trial.sh` (6 checks, all pass).
* **What works (verified by decoding the output and comparing pixels):**
  * *I-frame removal / classic datamosh* needs **no FFglitch**: stock FFmpeg `-c copy -bsf:v "noise=drop='key*gt(n,0)'"`. Frames before the cut are bit-identical, frames after smear the old picture along the new clip's motion (looked at the result: textbook mosh).
  * *Motion-vector editing*: `ffedit -i in.avi -f mv -s script.js -o out.avi`; JS (QuickJS) `glitch_frame(frame)` mutates `frame.mv.forward[row][col] = [x,y]`. Amplifying vectors x4 decodes cleanly and the error compounds over P-frames.
  * *Motion transfer*: export A's MVs (`-e a.json`), apply to B (`-a a.json`). Re-exporting the result gives exactly A's vectors on all 99 P-frames; the picture is B's pixels dragged by A's motion (B's residuals still apply on top, so it is smeary rather than clean).
* **Limits / gotchas:**
  * Supported codecs: MPEG-4 Part 2, MPEG-2, MJPEG, (see `ffedit -i file`). **H.264/H.265 are not supported** ("FFEdit does not support codec"). MP4, MKV and MPEG-PS containers are refused; AVI and raw `.m2v` work.
  * Vectors have a per-stream range (`f_code`). Scaling beyond it writes a corrupt stream (ffedit only warns "outside of range"). Fix: make the intermediate with FFglitch's own encoder: `ffgac ... -c:v mpeg4 -mpv_flags +nopimb+forcemv -g 9999 -bf 0 -fcode 6` (stock FFmpeg has no `-fcode`). Also clamp in scripts.
  * Source and target for transfer must have identical size/frame structure (same macroblock grid, same P-frame layout).
  * Script arrays are indexable but **not iterable** (`for...of` throws); use index loops.
  * Python scripting is mentioned in help but only JS was tried. Windows build not tried (ffglitch.org lists Windows builds; unverified).
* **How to drive it from FFWORKS (design, not built yet):** a "codec lab" job: (1) transcode the clip range to a disposable MPEG-4 AVI intermediate with `ffgac` (fcode 6, all-P), (2) run `ffedit` with a parameterised script (generated from the command JSON; params passed via `-sp`), (3) transcode the result back to the project's delivery format and import it as new media. Originals are never touched; each job records tool version, script and seed. UI must say plainly: output is a *new file* made from a lossy intermediate, not an effect on the live timeline. Needs ffglitch as an optional separately-downloaded GPL tool (like FFmpeg, found via settings/bundled/PATH), never linked.
